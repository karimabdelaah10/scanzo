# Decisions

Why the system is built the way it is. Each entry is a decision that would be
expensive to reverse later.

---

## 1. One database, `business_id` everywhere

**Decision:** a single MySQL database shared by all tenants, with a
`business_id` column on every table and a global scope on every model.

A database per tenant gives stronger isolation but multiplies migrations,
backups and connections, and the customers are small businesses, not banks.
If an enterprise customer ever demands physical isolation, that becomes a
separate deployment rather than a change to this model.

The tenant is resolved from the authenticated user after login, on a single
domain. Subdomains per business are a later feature, not a prerequisite.

---

## 2. One QR per variant, not per product

A model comes in sizes and colours, and each combination has its own price and
its own stock. So the label, the scan and the stock ledger all work at the
variant level. A QR on "linen shirt" with no size would be useless at the till.

---

## 3. The QR carries a code, not data

The label encodes the SKU (`SKU-10452`), nothing else. The name, price and stock
come from the system at scan time.

If the label carried the price, every price change would mean reprinting the
shop. It also keeps the code short enough to scan reliably from a small sticker.

We print a 1D barcode next to the QR on the same label, so a shop that later
buys a cheap USB scanner is not stuck.

---

## 4. UUID primary keys

**Decision:** UUIDs everywhere, generated by the device that creates the row.

Auto-increment ids need a central authority. A phone selling with no connection
cannot ask the server for the next id, and two devices doing so would collide on
reconnect. UUIDs let any device create a valid row at any time.

Invoice *numbers* are separate from ids and human-readable: the device code plus
a counter local to that device (`A1-000123`), which is also collision-free
offline.

The UUIDs must be **ordered** ones (Laravel's `HasUuids` trait) — see
[decision 11](#11-mysql-8) for why that matters on MySQL.

---

## 5. Stock is a ledger, not a column

**Decision:** `stock_movements` with signed quantities. The balance is the sum.

A single `quantity` column cannot be updated correctly by two offline devices.
With a ledger, both sales are recorded and both are valid; if they oversold, the
balance goes negative and the business sees it. A wrong number that can be
spotted is better than a sale that disappeared.

It also gives the stock history for free: what moved, when, who did it, and why.

---

## 6. Invoice lines keep their own copy of the price

`invoice_items` stores the product name, variant label, SKU and unit price as
they were at the moment of sale. Reading today's price when printing last
month's receipt would silently rewrite history, and a deleted variant would
break old invoices entirely.

---

## 7. Returns ship in the first version

Returns and exchanges happen every day in a clothing shop. Adding them later
would mean reworking invoices (to track what has already come back) and stock
(to accept inbound movements), so they are in from the start.

An exchange is modelled as a return plus a new invoice, linked together — not as
a third kind of transaction.

A return needs the original invoice, which has a consequence for the offline
mode: a device keeps the invoices of roughly the return window, and anything
older, or from another branch, needs a connection.

---

## 8. Offline selling, designed for now and built in phase two

The schema is offline-ready from the first migration — UUIDs, a stock ledger,
registered devices, and `issued_at` / `synced_at` on every transaction. The
sync engine itself is built in phase two, once the selling screen has been
through a real shop.

Building the schema for it later would mean rewriting the core tables; building
the sync engine now would mean debugging the hardest part of the system before
anyone has used the easy parts.

**What works offline:** scanning, selling, printing, and returns against
invoices held on the device. **What does not:** adding products, reports,
settings — those stay online, which keeps the sync one-directional for
catalogue data and much simpler.

A subscription has `offline_grace_days`. A device that has not synced in that
long stops selling, otherwise a shop could run indefinitely without paying.

---

## 9. Phone is a PWA, computer is a desktop app

The phone runs a web app in the browser: the camera works from the page, it
needs no store approval, and updates are instant. Requires HTTPS.

The computer gets the same Vue code wrapped in Electron or Tauri, which buys two
things the browser does not give: printing to a thermal receipt printer without
a dialog, and a dependable local database for offline mode. Scanning there is
done with a USB 2D scanner.

---

## 10. Labels are a PDF, not direct printing

The system produces a print-ready PDF — a label roll size or a grid on A4 — and
the printing is done by whatever the shop has: a Bluetooth label printer, a
Wi-Fi printer, or a print shop down the road.

Direct Bluetooth printing from the browser is Android-only, so it would leave
iPhone users with nothing. It can be added later as a convenience on top of the
PDF, never instead of it.

---

## 11. MySQL 8

Kept in line with the other projects on the same machines, so there is one
database engine to back up, tune and know well.

Two things follow from the choice and are not optional:

- **Ordered UUIDs.** InnoDB stores rows in primary-key order, so random UUID
  keys cause page splits and a fragmented index that gets worse as the table
  grows. Laravel's `HasUuids` trait generates ordered (time-prefixed) UUIDs;
  use it on every model and never `Str::uuid()` for a primary key.
- **`utf8mb4` everywhere**, set on the server in `docker-compose.yml`, so Arabic
  product names sort and compare correctly.

MySQL 8, not 5.7: 5.7 is end of life, and its `json` support and default
collations are both weaker.

## 12. The Laravel app lives in `core/`

The repository root holds infrastructure (`.docker/`, `scripts/`,
`docker-compose.yml`, `docs/`) and the application sits in `core/`. Same layout
as the courses project. It keeps the Docker data directory and the build config
out of the container's application mount.
